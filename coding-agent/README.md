# Coding agent с tool calling

Консольный агент для небольшого Python-проекта. Сам agent loop, проверка policy,
подтверждения, сохранение состояния, бюджеты, задачи и откат написаны вручную.
Готовых агентских фреймворков и сторонних Python-зависимостей нет.

Реализованы требования базовой части и дополнительных уровней 8–10.
Это перечень реализованных функций, а не гарантия оценки на защите.

**Подробный разбор:** [docs/explanation.md](docs/explanation.md).
**Соответствие условию и тестам:** [docs/requirements.md](docs/requirements.md).
**Сценарий защиты:** [docs/defense.md](docs/defense.md).
**Перед сдачей:** [docs/submission.md](docs/submission.md).

## Установка

Нужны Python **3.11+**, Bash и Linux/macOS/WSL. Команды выполняются из корня
репозитория — там находятся `policy.json` и папка `agent`.

```bash
python3 --version
bash --version
python3 -m unittest discover -s tests -v
```

Установка пакетов через pip не нужна; `requirements.txt` это явно фиксирует.
Тесты runtime используют временные копии проекта и не исправляют сдаваемый
`workspace/order.py`. В репозитории этот файл намеренно содержит исходную ошибку.

## Быстрая демонстрация без модели и API-ключа

Скопируйте контрольный проект, чтобы оставить исходный пример для повторной защиты:

```bash
cp -R workspace demo-workspace
python3 -m agent start --workspace demo-workspace --model demo --mode auto --run-id demo
```

Агент изучит файлы, сохранит структурированный план и завершит процесс со статусом
`wait_plan`. До утверждения плана файлы не меняются и Bash не запускается.

```bash
python3 -m agent approve-plan demo
python3 -m agent tasks demo
python3 -m agent diff demo
python3 -m agent rollback demo
```

После утверждения demo исправляет формулу, запускает **реальный Bash и реальные
unittest**, проверяет результаты задач и заканчивает работу. `rollback`
восстанавливает исходный `order.py`.

`--model demo` — **детерминированная замена модели**, а не нейросеть. Ответы этой
замены описаны в `agent/demo.py`. Она нужна для воспроизводимой демонстрации
runtime. По умолчанию используется `--model api`: решения принимает внешняя модель.
Демо не умеет придумывать альтернативное исправление после отказа пользователя.

## Настоящая модель

Подойдёт доступный вам сервис с Chat Completions API и function tool calling.
Название модели и адрес API берутся из окружения:

```bash
export OPENAI_BASE_URL='https://your-provider.example/v1'
export OPENAI_API_KEY='your-key'
export OPENAI_MODEL='your-tool-calling-model'
python3 -m agent start --workspace workspace --model api --mode safe --run-id real
```

Значения провайдера выше — заполнители. Платный ключ не требуется: используйте
учебный доступ или доступный бесплатный лимит. Ключ не передаётся Bash и не
сохраняется в состоянии запуска. `.env.example` — образец; автоматически `.env`
не загружается. Не добавляйте настоящий `.env`, ключи и `.runs` в Git.

Запасной локальный вариант из условия:

```bash
ollama pull qwen3:4b
ollama serve
```

Если Ollama уже работает в фоне, второй сервер запускать не нужно. В другом
терминале, из папки проекта:

```bash
export OPENAI_BASE_URL='http://localhost:11434/v1/'
export OPENAI_API_KEY='ollama'
export OPENAI_MODEL='qwen3:4b'
export OPENAI_TIMEOUT_SECONDS='600'
export OPENAI_REASONING_EFFORT='none'
python3 -m agent start --model api --mode safe --run-id local
```

`OPENAI_TIMEOUT_SECONDS` задаёт время ожидания HTTP-ответа в секундах: по умолчанию
90, для медленной локальной модели в примере — 600. Значение должно быть конечным
положительным числом. Это отдельный лимит от таймаута Bash в policy.
`OPENAI_REASONING_EFFORT=none` отключает thinking у Qwen3 через Ollama, сокращая
время генерации. Для другого провайдера задавайте поддерживаемое им значение
или уберите переменную: без неё поле `reasoning_effort` не отправляется.
После `model_error` можно выполнить `resume` с тем же run_id и новыми настройками;
уже потраченный бюджет сохраняется.

Для локальной Qwen3 при `OPENAI_REASONING_EFFORT=none` адаптер также добавляет
`/no_think` в HTTP-запрос, не меняя сохранённую историю. Локальная Qwen3 получает
лимит ответа 2048 токенов; его можно изменить через `OPENAI_MAX_TOKENS`.
Ответ с `finish_reason=length` считается ошибкой. CLI печатает начало и завершение
каждого запроса к настоящей модели, чтобы был виден прогресс.

Если базовая Qwen3 долго рассуждает или не переходит к инструментам, можно
использовать профиль Qwen3 Instruct с контекстом 8192 токена:

```bash
ollama pull qwen3:4b-instruct
ollama create qwen3-workshop -f examples/Ollama.Modelfile
export OPENAI_MODEL='qwen3-workshop'
export OPENAI_REASONING_EFFORT='none'
export OPENAI_TIMEOUT_SECONDS='120'
```

После неудачного прогона с длинными текстовыми ответами начните новый `run_id`
на чистой копии workspace, чтобы эти ответы не занимали контекст модели.

Качество плана и исправления зависит от выбранной модели. Ошибочный вызов
инструмента возвращается ей для исправления; лимиты не дают циклу работать
бесконечно. Маленькая локальная модель может не справиться с первого раза.

HTTP-адаптер протестирован с локальным тестовым сервером и настоящей локальной
Qwen3 Instruct через профиль `qwen3-workshop`. Прогон `real-accepted-20261014`
завершился `completed`: модель сама записала исправление, оба исходных теста
прошли через Bash, `test_order.py` остался неизменным. Первый план был отклонён
с просьбой сначала прочитать тесты; после этого модель прочитала их и обновила
план. Краткий результат сохранён в [examples/live-session.txt](examples/live-session.txt).
Перед защитой повторите запуск на своей машине. Платные внешние API не проверялись.

## CLI и подтверждения

`RUN_ID` ниже заменяется на напечатанный идентификатор запуска. При `--run-id demo`
это просто `demo`. Повторно создавать уже существующий `run_id` нельзя.

| Команда | Действие |
|---|---|
| `python3 -m agent start --task '...' --mode safe` | Новый запуск, сначала Plan Mode |
| `python3 -m agent status RUN_ID` | Статус, бюджет, план или ожидающее действие |
| `python3 -m agent approve-plan RUN_ID` | Утвердить план и продолжить |
| `python3 -m agent reject-plan RUN_ID --reason '...'` | Отклонить план, вернуть модель к планированию |
| `python3 -m agent approve RUN_ID` | Разрешить конкретный ожидающий tool call |
| `python3 -m agent deny RUN_ID --reason '...'` | Отказать; модель получит причину и сможет выбрать другой шаг |
| `python3 -m agent resume RUN_ID` | Продолжить тот же запуск; ожидания не обходятся |
| `python3 -m agent tasks RUN_ID` | Чеклист задач |
| `python3 -m agent diff RUN_ID` | Изменения этого запуска и SHA-256 |
| `python3 -m agent rollback RUN_ID` | Явно откатить изменения; завершает запуск |

CLI останавливается на подтверждении, сохранив состояние. Его не нужно держать
запущенным в другом терминале. Утверждение плана **не** заменяет подтверждения
действий в `safe`.

| Действие | Plan Mode | `safe` после плана | `auto` после плана |
|---|---|---|---|
| Чтение/список файлов | Сразу | Сразу | Сразу |
| Запись | Запрещена | Подтверждение | Сразу после проверок |
| Bash | Запрещён | Подтверждение | Сразу после проверок |
| Удаление | Запрещено | Подтверждение | Подтверждение |

Все новые запуски начинаются в отдельной фазе `plan`. Переход в фазу `execute`
возможен только через `approve-plan`. Это осознанно обязательное планирование,
а не флаг, который модель может отключить.

Папка состояния по умолчанию — `.runs` вне workspace. Другой путь задаётся
**перед подкомандой**, и его нужно использовать во всех последующих командах:

```bash
python3 -m agent --state-dir my-runs start --model demo --run-id another
python3 -m agent --state-dir my-runs approve-plan another
```

## Инструменты

| Имя | Аргументы | Результат/ограничения |
|---|---|---|
| `list_files` | `path` | Один уровень разрешённых файлов/директорий |
| `read_file` | `path` | UTF-8 текст, признак обрезки |
| `write_file` | `path`, `content` | Полная атомарная замена/создание файла, SHA-256 |
| `delete_file` | `path` | Удаление одного файла; всегда подтверждается |
| `Bash` | `command`, `cwd` | `stdout`, `stderr`, `exit_code`, `timed_out`, `truncated` |
| `submit_plan` | Структура плана | Сохраняет план и запрашивает решение человека |
| `finish_task` | `summary` | Runtime проверяет фактический результат задачи |

В фазе исполнения к каждому вызову добавляется `task_id`. Во время планирования
его быть не должно. Набор инструментов передаётся API с описаниями и JSON Schema.
В планировании модель получает только инструменты чтения и `submit_plan`, без
поля `task_id`. При исполнении `task_id` обязателен в схемах и ограничен точным
идентификатором текущей задачи. Runtime дополнительно проверяет эти ограничения.
Модели показываются инструменты текущей задачи и `finish_task`. Когда runtime
уже подтвердил результат задачи, доступен только `finish_task`; после завершения
всех задач модель получает запрос на финальный текст без инструментов.
Собственный валидатор реализует ровно используемое подмножество JSON Schema,
а не претендует на поддержку полного стандарта.

`write_file` не создаёт родительские директории. Пути относительны workspace.
Двоичные файлы сохраняются в снимках для отката, но инструмент записи принимает
только текст. Проект ограничен 16 MiB, отдельный файл снимка — 2 MiB.

## Policy

`policy.json` лежит вне workspace. При запуске запоминается SHA-256 policy;
изменение конфигурации посреди запуска блокирует дальнейшие действия. Для новых
правил нужен новый запуск. Перед **каждым исполнением** policy читается снова.

```json
{
  "commands": {
    "allow": ["python3 -m unittest -v", "python3 -m unittest", "pwd"],
    "deny": ["rm -rf .", "bash -c pwd"]
  },
  "directories": {"allow": ["."], "deny": ["private"]},
  "read_only": ["test_*.py", "*/test_*.py", "*_test.py", "*/tests/*"],
  "bash_timeout": 10,
  "max_output_bytes": 16384
}
```

Директории конфига относительны workspace и канонизируются runtime. Запрет
приоритетнее разрешения. Абсолютные пути, `..`, симлинки и hard links отвергаются.
Тесты дополнительно защищены от записи/удаления файловыми инструментами.
Запрещённая директория `private` не читается и не входит в снимки.

Команды сравниваются **целиком**, с аргументами. Для Bash есть дополнительная
небольшая грамматика и список поддерживаемых форм команд в `Policy.SUPPORTED`.
Добавление `bash -c ...`, конвейера, подстановки или команды с путём в allow не
обходит этот барьер. Расширение форм команд требует изменения проверяющего кода.

Bash запускается без startup-файлов, с очищенным окружением, ограничением времени
и суммарного stdout/stderr. При таймауте/переполнении завершается вся группа
процессов. Установлен `PYTHONDONTWRITEBYTECODE=1`: штатные тесты не создают pyc.
Исключений для генерируемых файлов в снимках **нет**: новые файлы внутри разрешённой
области тоже фиксируются.

**Граница безопасности:** это policy, не системная песочница. Python-тесты и
импортируемый ими код имеют права пользователя и технически могут обратиться
за пределы workspace. Запускайте только учебную копию без секретов. Для
враждебного кода понадобятся контейнер/VM и ограничения ОС. Конкурирующие
запуски нашего CLI блокируются lock; защита от злонамеренных гонок внешнего
процесса между проверкой и открытием файла не заявляется.

## Бюджеты

По умолчанию: 40 запросов модели, 100 tool calls, 20 побочных действий, 131072
байта результатов инструментов. Настройка — JSON с любыми из этих ключей:

```json
{"model_calls": 40, "tool_calls": 100, "side_effects": 20, "result_bytes": 131072}
```

```bash
python3 -m agent start --model demo --limits examples/limits.json --run-id budget-demo
```

Счётчики общие для планирования, исполнения и восстановления. `resume` их не
обнуляет. Вся пачка tool calls проверяется перед исполнением; нехватка бюджета
не позволяет выполнить даже первый вызов пачки. Для каждого результата
резервируются минимум 128 байт. Размер считается по реально сохранённому
UTF-8 `content` сообщения `role: tool`, включая JSON-обёртку.

Если остаток недостаточен для полного вывода, executor получает этот остаток,
а runtime дополнительно обрезает сериализованный результат с `truncated: true`.
Для Bash прерывание по лимиту вывода считается неуспешным выполнением.

## Сбой и восстановление

Перед выполнением сохраняются `started`, номер попытки, снимок и списание
бюджета. После выполнения — результат и фактические изменения. Если процесс
упал между ними, вызов становится `uncertain`, а не выполняется заново.

```bash
python3 -m agent resume RUN_ID
python3 -m agent uncertain-diff RUN_ID
python3 -m agent resolve RUN_ID retry --adopt-changes
# Или:
python3 -m agent resolve RUN_ID fail --adopt-changes
python3 -m agent resolve RUN_ID abort
```

`--adopt-changes` нужен только когда обнаружены изменения: пользователь явно
относит их к данному запуску. Если он не согласен, можно завершить запуск с
ошибкой. Неопределённые изменения не откатываются молча.

Повтор разрешён для чтения и полной записи тех же сохранённых байтов.
**Bash и удаление автоматически повторяемыми не считаются.** Выберите `fail`
или `abort`. После `fail` настоящая модель может предложить новый проверочный
вызов. После `abort` запуск завершён с ошибкой; неопределённые эффекты по-прежнему
блокируют откат. Для продолжения работы нужен новый запуск/ручной разбор файлов.

Обычный повтор завершённого `tool_call_id` возвращает сохранённый результат без
повторного эффекта. То же id с другим именем/аргументами даёт ошибку протокола.
Явный `retry` создаёт новую попытку этого id, не возвращая потраченный бюджет.

Для демонстрации сбоя используйте safe-demo: сначала `start`, затем
`approve-plan`, дождитесь подтверждения записи, после чего:

```bash
python3 -m agent approve RUN_ID --crash-at after_execute
python3 -m agent resume RUN_ID
```

Код выхода имитации — 99. Точки отказа: `after_charge`, `after_execute`,
`after_model_charge`, `rollback_after_start`, `rollback_after_file`.
Имитация выбрасывает исключение, минуя обычную обработку ошибок инструмента;
CLI завершается, следующий вызов читает состояние с диска.

## План, зависимости и результат задачи

План содержит `goal`, `tasks`, `risks`, `assumptions`, `done_when`.
У задачи: `id`, `description`, `depends_on`, `tools`, `result`.
Runtime проверяет уникальность id и отсутствие циклов. Исполнение последовательное.

Пример: `inspect` → `fix` → `test`. Пока `inspect` не подтверждена,
вызов с `task_id: fix` запрещён. Чеклист: `[ ]` ожидает, `[>]` исполняется,
`[x]` выполнена. Фактические свидетельства сохраняются в `actual_result`.

Результат проверяется по событиям runtime:

- `read`: нужные файлы успешно прочитаны инструментом в этой задаче;
- `file`: запись реально выполнена; текущий SHA-256 совпадает с результатом;
- `absent`: удаление реально выполнено, файла больше нет;
- `tests`: Bash запустил указанную unittest-команду, успешно выполнил хотя бы
  один тест, и дерево с тех пор не изменилось.

Перед финальным завершением свидетельства проверяются ещё раз. Если после
успешных тестов код был изменён, старый результат тестов не доказывает готовность.
`finish_task` не является утверждением «поверить модели на слово».

## Diff и откат

Хранятся исходные байты, последние байты, права файлов, SHA-256 и события
изменений. Bash тоже обёрнут снимками. Перед следующим побочным действием
внешнее изменение любого файла разрешённого дерева приводит к остановке.

Перед откатом проверяются policy и хеши **всех** затронутых файлов. При конфликте
не перезаписывается ни один файл. Посторонние файлы, которые запуск не менял,
откат не трогает. Список файлов снимка позволяет отличать создание и удаление.

Откат нескольких файлов не является одной атомарной транзакцией файловой
системы. На случай падения сохраняется намерение отката: статус
`rollback_uncertain`. Повторите **явную** команду `rollback RUN_ID`; runtime
проверит, что каждый файл равен либо последней версии агента, либо уже
восстановленной исходной версии. При ином содержимом остановится. `resume`
такой откат самостоятельно не продолжает.

## Проверки и ограничения

```bash
python3 -m unittest discover -s tests -v
```

Проверяются полный демо-прогон, policy, схемы, подтверждения, границы бюджетов,
сбои, зависимости, журнал, откат, таймауты, лимит вывода, HTTP-протокол и CLI
в отдельных процессах. Тесты не обращаются к интернету и не требуют ключей.
GitHub Actions запускает эту же команду.

Ограничения намеренные: только обычные файлы и существующие директории,
последовательный scheduler, узкий Bash, один активный CLI на workspace,
небольшое дерево. JSON-хранилище рассчитано на локальную файловую систему с
обычной семантикой `fsync`/`os.replace`, а не на сетевой диск. Policy и `.runs`
доверенные: человек, который может подменить сам runtime или его состояние,
находится за границей рассматриваемой модели угроз.
