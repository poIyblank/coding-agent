# Разбор проекта: от идеи до защиты

Этот файл лучше читать рядом с кодом. Не пытайся сразу запомнить весь `runtime.py`.
Сначала пойми, какие решения он принимает, затем найди соответствующие методы.

## 1. Что вообще нужно сделать

Обычная программа выполняет заранее заданные действия. Например:

```python
read_file("order.py")
write_file("order.py", fixed_code)
run_tests()
```

Такой скрипт умеет исправить один известный файл. Но это ещё не агент.

В агенте программист заранее задаёт **доступные действия и правила**, а модель
на каждом шаге выбирает, что делать дальше. Она может сначала посмотреть список
файлов, затем прочитать тесты, затем код, ошибиться, получить сообщение об ошибке
и попробовать другой шаг.

При этом модель ничего не запускает сама. Она возвращает данные примерно такого вида:

```json
{
  "id": "call_17",
  "type": "function",
  "function": {
    "name": "read_file",
    "arguments": "{\"path\":\"order.py\",\"task_id\":\"inspect\"}"
  }
}
```

Это заявка: «вызови `read_file` с такими аргументами». `arguments` здесь — строка,
внутри которой лежит JSON. Поэтому сначала нужен `json.loads`, затем проверка схемы.
Нельзя считать строку уже проверенным Python-словарём.

Наш код может ответить заявке отказом. Например, модель попросила `../policy.json`,
неправильный инструмент или запись до утверждения плана. То, что модель захотела
сделать действие, не даёт ей права его выполнить.

**Главная идея всей работы:** модель выбирает следующий шаг, runtime решает,
допустим ли этот шаг, а executor выполняет разрешённое действие.

## 2. Почему это больше, чем цикл вокруг ChatGPT

Представь, что модель предложила записать файл. Нужно ответить сразу на несколько
вопросов:

1. Есть ли вообще такой инструмент?
2. Правильные ли аргументы? `path` — строка или случайно число?
3. Файл внутри workspace? Не ведёт ли путь через ссылку наружу?
4. Сейчас планирование или исполнение?
5. Можно ли этой задаче использовать этот инструмент?
6. Нужно ли согласие пользователя?
7. Есть ли бюджет?
8. Не изменил ли кто-то проект с прошлого шага?
9. Что сохранить до записи, чтобы пережить падение?
10. Как вернуть результат модели и не выполнить запись второй раз после перезапуска?

Для этого и нужен runtime — код, который управляет жизнью одного запуска агента.
В задании оценивают в основном эти вопросы. Сама формула скидки — контрольный пример.

## 3. Где что находится

| Файл | За что отвечает | Откуда начать читать |
|---|---|---|
| `agent/cli.py` | Команды терминала, печать статуса и чеклиста | `parser`, `execute` |
| `agent/model.py` | Один HTTP-запрос к модели | `APIModel.complete` |
| `agent/schema.py` | Описания инструментов, проверка аргументов | `DEFINITIONS`, `parse_arguments` |
| `agent/policy.py` | Пути, команды, режимы, запреты | `path`, `command`, `check` |
| `agent/executor.py` | Реальное чтение/запись/удаление/Bash | `Executor.execute`, `run_bash` |
| `agent/storage.py` | Атомарный JSON и блокировка процессов | `atomic_bytes`, `Store` |
| `agent/journal.py` | Снимки, хеши, diff, восстановление файла | `snapshot`, `changed` |
| `agent/runtime.py` | Связывает всё выше | `drive`, затем `step` |
| `agent/demo.py` | Заранее заданные ответы для воспроизводимой проверки | `DemoModel.complete` |

Не нужно говорить на защите, что здесь какая-то особенная «мультиагентная система».
Здесь один агент, последовательное выполнение и достаточно простой scheduler.
Разделение модулей нужно, чтобы решение модели не смешивалось с проверкой безопасности.

## 4. Исправление контрольного проекта

Исходная функция:

```python
def calculate_total(prices: list[float], discount_percent: float) -> float:
    return sum(prices) - discount_percent
```

При ценах 100 и 50 сумма равна 150. Скидка 10 процентов — это 15, а исходный код
вычитает просто 10. Поэтому получается 140 вместо 135.

Исправление:

```python
def calculate_total(prices: list[float], discount_percent: float) -> float:
    if not 0 <= discount_percent <= 100:
        raise ValueError("discount_percent must be between 0 and 100")
    return sum(prices) * (1 - discount_percent / 100)
```

`discount_percent / 100` превращает 10 процентов в долю 0.1. После скидки нужно
заплатить долю `1 - 0.1 = 0.9`. Значит, `150 * 0.9 = 135`.

`0 <= x <= 100` — проверка диапазона с включёнными границами. Если скидка −1 или
101, функция должна выбросить `ValueError`: именно это проверяет второй тест.
При скидке 0 платим всю сумму, при 100 — ноль. Пустой список даёт сумму 0.

Мы не добавляем произвольное округление до двух знаков: такого требования нет,
и это изменило бы поведение функции. Для реальных денег обычно отдельно
выбирают денежный тип и правила округления, но это уже другая задача.

В сдаваемом `workspace/order.py` намеренно лежит **неисправленная** функция.
Иначе демонстрация не показала бы, что именно агент нашёл и исправил ошибку.
Исправленный текст есть в демо и появляется после запуска настоящего агента.

## 5. Как модель узнаёт, какие инструменты есть

Каждый инструмент передаётся вместе с описанием и JSON Schema. Например:

```json
{
  "type": "function",
  "function": {
    "name": "read_file",
    "description": "Read a UTF-8 file in the workspace.",
    "parameters": {
      "type": "object",
      "properties": {
        "path": {"type": "string", "maxLength": 2000},
        "task_id": {"type": "string", "maxLength": 64}
      },
      "required": ["path"],
      "additionalProperties": false
    }
  }
}
```

Схема объясняет форму аргументов. Она не доказывает, что путь безопасен.
Например, `"../../secret.txt"` — корректная строка, но недопустимый путь.
Поэтому схема и policy — **две отдельные проверки**.

`additionalProperties: false` означает, что модель не может незаметно добавить
непредусмотренные аргументы вроде `ignore_policy: true`.

В проекте нет зависимости от `jsonschema`: используется небольшой валидатор
конкретного подмножества схем. Он проверяет типы, обязательные поля, лишние
поля, перечисления, размеры строк/массивов и числовые границы. Мы не используем
`$ref`, `oneOf` и другие части полного стандарта и не утверждаем, что поддерживаем их.

`task_id` не обязательный на уровне общей схемы, потому что при планировании
задача ещё не выполняется. Runtime отдельно требует его на фазе исполнения.

## 6. Agent loop пошагово

Основной метод — `Runtime.drive`. Упрощённо:

```python
while status == "running":
    if есть_сохранённые_tool_calls:
        обработать_следующий_вызов()
        continue

    проверить_бюджет_модели()
    списать_один_запрос_и_сохранить()
    ответ = модель.complete(история + текущее_состояние)
    принять_ответ(ответ)
```

Это именно схема для понимания; полный рабочий код находится в `runtime.py`.

Важна проверка очереди **до** нового запроса модели. После сбоя могут остаться
ещё не обработанные вызовы из уже полученного ответа. Нужно продолжить их,
а не забыть и спросить модель заново.

История разговора выглядит так:

1. `system`: правила агента.
2. `user`: задача пользователя.
3. `assistant`: модель попросила два инструмента.
4. `tool`: результат первого, с его `tool_call_id`.
5. `tool`: результат второго, с его `tool_call_id`.
6. `assistant`: следующее решение модели.

У вызова может быть свой произвольный id вроде `call_abc`. Мы возвращаем именно
его, а не создаём новый: иначе модель/API не смогут однозначно связать результат
с запросом.

Несколько вызовов в одном ответе поддерживаются, но исполняются последовательно.
Параллельность условием не требуется и усложнила бы согласование изменений файлов.

Если инструмента нет или он упал с обычной ошибкой, модель получает, например:

```json
{"ok": false, "error": "FileNotFoundError: ..."}
```

Цикл не завершается из-за того, что модель ошиблась именем файла. У неё есть шанс
прочитать список файлов и исправить свой следующий вызов.

Финальный текст допускается только после успешного завершения задач. «Я всё
сделал» до подтверждённых результатов не превращает запуск в успешный.

## 7. Почему нужна копия списка вызовов

В `accept` история и рабочая очередь не должны ссылаться на один изменяемый список.
Иначе `batch.pop(0)` удалит вызов не только из очереди, но и из старого сообщения
`assistant`. Сохранённая история получится неправильной: результаты `tool` есть,
а соответствующие вызовы из истории исчезли.

Поэтому очередь создаётся отдельной копией:

```python
self.s["batch"] = json.loads(json.dumps(calls))
```

Это простой способ скопировать вложенные JSON-данные. Здесь нет Python-объектов,
которые потеряли бы смысл после сериализации. Автотест отдельно проверяет,
что после исполнения в истории остаются исходные `tool_calls`.

## 8. Проверка путей

Одной проверки `path.startswith("workspace")` недостаточно.

- `workspace/../secret` внешне начинается с workspace, но выходит наружу.
- `workspace/link/file` может вести через симлинк в другую директорию.
- Абсолютный путь вообще не должен зависеть от текущей директории процесса.
- Hard link может дать другое имя тем же данным за пределами разрешённого дерева.

Наш порядок:

1. Требуем непустой относительный путь без компонента `..`.
2. Проходим компоненты и запрещаем симлинки.
3. Получаем канонический путь через `resolve()`.
4. Проверяем, что он внутри workspace и хотя бы одной allow-директории.
5. Проверяем, что он не внутри deny-директории.
6. Для обычного файла запрещаем количество hard links больше одного.
7. Для записи отдельно применяем `read_only`.

В этом учебном проекте даже симлинк на другой разрешённый файл запрещён. Это
более строгое, зато простое и объяснимое правило.

Allow означает «можно при соблюдении остальных условий», а не «обойти deny».
Если корень разрешён, а `private` запрещён, `private/README.txt` читать нельзя.

`policy.json` и `.runs` находятся **вне workspace**. Поэтому модель не может
через `write_file` расширить собственные разрешения или обнулить счётчики.
Дополнительно runtime сверяет хеш policy при каждом действии и при загрузке.

## 9. Проверка Bash: почему нельзя смотреть первое слово

Допустим, разрешено `python3`. Тогда такая проверка ошибочно пропустит:

```text
python3 -c "...произвольный код..."
python3 -m unittest; другая-команда
python3 -m unittest > важный-файл
```

Риск находится и в аргументах, и в синтаксисе оболочки.

У нас три барьера:

1. Команда не должна быть в `commands.deny`.
2. Вся строка должна точно совпадать с `commands.allow`.
3. Строка должна соответствовать простой грамматике и одной из заранее
   поддерживаемых форм `Policy.SUPPORTED`.

Разрешены `python3 -m unittest -v`, `python3 -m unittest` и `pwd`.
Никаких `;`, `|`, `>`, `$()`, кавычек, `bash -c`, путей в аргументах.
Рабочая директория `cwd` проверяется отдельно тем же механизмом путей.

Именно поэтому добавление опасной строки в allow само по себе не делает её
поддерживаемой. Чтобы расширить набор команд, придётся явно расширить проверяющий код.

Но разрешённые тесты — тоже код. Импортируемый `order.py` теоретически может
читать произвольные файлы пользователя. **Проверка команды не изолирует процесс.**
Мы ограничиваем заявки модели и фиксируем изменения, но не строим контейнер.
Это честная граница работы, прямо соответствующая предупреждению в условии.

## 10. Как ограничен процесс Bash

`run_bash` использует `subprocess.Popen`. Мы запускаем именно Bash, а не имитируем
его вызовом Python-функции. Команда передаётся Bash только после всех проверок.

Потоки stdout/stderr читаются через `selectors`, небольшими кусками. Почему не
просто `communicate()` без ограничений? Процесс может бесконечно печатать данные,
а родитель — накопить их целиком в памяти.

Здесь есть:

- общий лимит вывода для двух потоков;
- дедлайн по монотонным часам;
- отдельная группа процессов;
- уничтожение группы при таймауте/переполнении;
- закрытый stdin, чтобы тесты не ждали ввода;
- очищенное окружение без API-ключа и startup-настроек Bash/Python.

`monotonic()` нужен потому, что системные часы можно перевести. Для измерения
прошедшего времени это не должно продлевать или сокращать таймаут.

Группа процессов нужна, чтобы завершить не только оболочку, но и её дочерние
процессы. Иначе дочерний процесс мог бы продолжить работать или держать поток открытым.

Превышение вывода даёт `truncated: true`, а выполнение не считается успешным.
Обрезанный вывод тестов не используется как доказательство прохождения.

## 11. Safe и auto

`safe` означает: сначала показать пользователю конкретное побочное действие,
сохраниться, выйти. Пользователь потом вводит `approve` или `deny`.

Сохраняется не просто флаг «ждём». Сохраняются id вызова, имя, точные аргументы,
текущая задача и вся предыдущая история. Поэтому после запуска нового процесса
понятно, **какую именно запись** человек разрешает.

После подтверждения policy и аргументы проверяются снова. Между запросом и
подтверждением могли поменяться файлы или конфигурация.

`auto` пропускает ручное подтверждение записи и Bash, но не пропускает policy,
проверку состояния и бюджет. Удаление в обоих режимах подтверждается отдельно.

При отказе мы не просто прекращаем всё навсегда: возвращаем модели результат
`User denied action: причина`. Настоящая модель может выбрать менее широкое
изменение, прочитать другой файл или объяснить, почему задача заблокирована.

Детерминированное демо такой интеллектуальной адаптации не изображает: его
сценарий известен заранее. Поведение после отказа проверяется отдельным тестом,
где следующим ответом предлагается безопасное чтение.

## 12. Состояние запуска

`run_id` — ключ, по которому находится один запуск. По умолчанию это короткий UUID.
Можно задать понятное имя через `--run-id defense`.

В `.runs/RUN_ID.json` хранятся:

| Поле | Зачем |
|---|---|
| `messages` | Что уже знает модель |
| `batch` | Какие calls из текущего ответа ещё нужно обработать |
| `calls` | Состояние и результаты вызовов по id |
| `decisions` | Решения пользователя и причины |
| `phase`, `status` | Планирование/исполнение и причина остановки |
| `limits`, `spent` | Общие лимиты и расход |
| `plan`, `tasks` | План, зависимости, прогресс, свидетельства |
| `initial_tree`, `expected_tree` | Исходное и последнее зафиксированное дерево |
| `events` | Фактические изменения действий |
| `rollback` | Есть ли незаконченный откат |

Состояние не хранится внутри проекта, который редактирует модель.
У него может быть чувствительное содержимое: тексты прочитанных файлов и снимки.
Поэтому `.runs` исключена из Git.

## 13. Почему нельзя сохранять JSON обычным `write_text`

Представь, что файл состояния уже был записан, а новый `write_text` сначала его
обрезал. После этого процесс упал. На диске остался обрывок JSON, из которого
невозможно восстановить запуск.

В `atomic_bytes` новый файл сначала целиком пишется во временный файл рядом:

1. `write` — записать байты;
2. `flush` — вытолкнуть буфер Python;
3. `fsync` — запросить сохранение данных;
4. `os.replace` — атомарно заменить старое имя новым файлом;
5. `fsync` родительской директории — зафиксировать изменение записи каталога.

Для обычной локальной файловой системы читатель увидит либо прежний JSON,
либо новый, но не наполовину переписанный документ. На особых сетевых файловых
системах нельзя безоговорочно обещать те же гарантии.

Весь state хранится одним документом специально: списание бюджета и изменение
статуса можно зафиксировать **одной** заменой. Если бы это были два независимых
файла, процесс мог бы успеть сохранить один и не успеть второй.

## 14. Самая важная проблема: действие уже случилось, а запись результата — нет

Для побочного действия порядок такой:

```text
сохранить started и потраченный бюджет
выполнить действие
сохранить результат и фактическое дерево
```

Между вторым и третьим пунктами может произойти сбой.
Например, файл уже изменён, но в JSON осталось `started`.

После перезапуска нельзя честно сказать ни «действие точно не выполнялось»,
ни «результат точно был успешным». Поэтому состояние называется `uncertain`.

Почему не повторить автоматически? Запись может быть безвредной, но Bash мог
отправить запрос, добавить строку, создать файл или выполнить другой неповторяемый
эффект. Из локального журнала нельзя доказать, что ничего не произошло.

Пользователь выбирает:

- `retry`: новую попытку, если тип инструмента признан повторяемым;
- `fail`: предыдущая попытка неуспешна, сообщить это модели и продолжить;
- `abort`: закончить запуск с ошибкой.

В нашей реализации повторяемы чтение и полная запись **тех же** байтов.
Повторная запись `content=X` снова даёт X. Это называется идемпотентностью:
два одинаковых действия дают тот же результат, что одно, в рассматриваемой
файловой модели. Добавление строки в конец таковым бы не было.

Перед повтором записи всё равно проверяются текущие файлы, policy и бюджет.
Bash не объявлен идемпотентным даже для тестов: это произвольный запускаемый код.

## 15. Почему одного `tool_call_id` недостаточно без аргументов

Предположим, сохранено:

```text
id = abc, write_file(order.py, "версия 1") → done
```

Модель опять прислала `abc` с теми же аргументами. Мы возвращаем старый результат,
не выполняя запись повторно.

Но если она прислала `abc` с `"версия 2"`, возвращать старый успех нельзя: это
уже другое действие. Выполнять новое тоже нельзя: id считается уже завершённым.
Runtime возвращает ошибку протокола.

Для сравнения хранится fingerprint: имя плюс JSON аргументов с отсортированными
ключами. Поэтому перестановка ключей объекта не делает действие «новым».
А изменение пути, текста или `task_id` делает.

При явном разрешённом `retry` id сохраняется, но в `attempts` добавляется новая
попытка. Так мы отличаем разрешённый человеком повтор от случайного дубликата.

## 16. Plan Mode

Планирование — отдельная фаза. Модель может читать файлы, но не может выполнять
Bash, даже если ей кажется полезным «только запустить тесты».

Почему Bash запрещён целиком? Заранее нельзя гарантировать отсутствие эффектов
у выполняемого кода. На фазе планирования нужны только инструменты чтения.

План хранится структурой, а не красивым абзацем:

```json
{
  "goal": "Исправить расчёт заказа",
  "tasks": [
    {
      "id": "inspect",
      "description": "Прочитать код и тесты",
      "depends_on": [],
      "tools": ["read_file"],
      "result": {"kind": "read", "paths": ["order.py", "test_order.py"]}
    }
  ],
  "risks": ["Не менять тесты"],
  "assumptions": ["Скидка задаётся в процентах"],
  "done_when": "Исправление проверено исходными тестами"
}
```

Это сокращённый пример структуры, не полный план исправления. Полный план из
трёх задач находится в `agent/demo.py`.

`submit_plan` сохраняет структуру и переводит запуск в `wait_plan`.
`approve-plan` разрешает переход к исполнению. `reject-plan` возвращает модель к
планированию вместе с причиной. Потраченные на предыдущий план ресурсы не исчезают.

## 17. Зачем сразу четыре бюджета

Разные лимиты останавливают разные виды проблемы:

| Бюджет | От чего защищает |
|---|---|
| `model_calls` | Бесконечный разговор с моделью, запросы без прогресса |
| `tool_calls` | Бесконечное чтение, ошибки, очень большие пачки действий |
| `side_effects` | Слишком много записей, удалений и запусков программ |
| `result_bytes` | Раздувание истории огромными результатами инструментов |

Число запросов — не то же самое, что число токенов или точная денежная стоимость.
Это требуемый для задания простой лимит. Токенный бюджет можно добавить, но он
не заменяет ограничения инструментов.

Когда списываем:

- запрос модели — до HTTP-запроса, затем сразу сохраняемся;
- tool calls — всей принятой пачкой вместе с очередью и сообщением assistant;
- побочное действие — вместе с `started` перед реальным выполнением;
- байты результата — вместе с сообщением `tool` и завершением вызова.

Если сеть упала после отправки запроса, нельзя уверенно сказать, что провайдер
не обработал его. Поэтому запрос не возвращается в бюджет. При сбое после
записи `started` аналогично не возвращается счётчик побочных действий.

## 18. Почему пачку проверяем целиком

Пусть остался бюджет на одну запись, а модель прислала две записи в одном ответе.
Если выполнить первую и только потом проверить вторую, получится частично
принятая пачка, хотя условие требует не выполнять ни одного вызова в такой ситуации.

Поэтому `accept` заранее подсчитывает потребности пачки. Если недостаточен хотя
бы один из проверяемых бюджетов, очередь вообще не принимается к исполнению.

Это **не** означает транзакцию всех файлов: если лимита хватало, но второй
инструмент вернул ошибку, первый автоматически не откатывается. Условие требует
целостной проверки ресурсов, а не автоматического отката любого неудачного пакета.

Повтор уже завершённого вызова тратит ещё один tool call и байты повторно
переданного результата, но не создаёт новый побочный эффект.

## 19. Как ограничивать размер результата, которого ещё нет

Нельзя узнать размер stdout до запуска команды. Решение — передать инструменту
доступный максимум и читать не больше этого максимума.

Есть ещё тонкость: строка stdout после упаковки в JSON становится длиннее.
Добавляются ключи, кавычки, экранирование переводов строк. Русские буквы и emoji
также занимают разное число байтов UTF-8, поэтому `len(text)` недостаточно.

`wire_result` считает именно `len(serialized.encode("utf-8"))`.
Если полная JSON-строка не помещается, возвращается компактная обёртка:

```json
{"ok": true, "truncated": true, "preview": "...часть исходного результата..."}
```

Длина preview подбирается двоичным поиском. Задача проста: найти максимальную
длину префикса, которая ещё помещается в бюджет с учётом JSON-обёртки.

Для оставшихся вызовов пачки резервируются минимум 128 байт на результат.
Первый огромный вывод не может съесть абсолютно всё и оставить следующие calls
без возможности вернуть даже короткое сообщение об ошибке.

## 20. Как runtime управляет задачами

У плана есть задачи. У задачи есть зависимости. Это ориентированный граф:

```text
inspect зависит от никого
fix зависит от inspect
test зависит от fix
```

В данном примере это обычная последовательность. Код также поддерживает
несколько независимых задач; они всё равно исполняются по одной.

Scheduler выбирает первую pending-задачу, у которой все зависимости уже done.
Других активных задач одновременно нет. Вызов с чужим `task_id` отвергается.

На этапе принятия плана проверяем:

- уникальность идентификаторов;
- существование всех зависимостей;
- отсутствие зависимости от самой себя;
- отсутствие циклов.

Цикл вроде `A зависит от B`, `B зависит от A` означает, что начать нельзя ни с одной.
Проверка постепенно добавляет задачи, чьи зависимости уже достижимы. Если после
остановки остались недобавленные задачи, план содержит цикл.

## 21. Почему `finish_task` недостаточно просто вернуть success

Модель может ошибаться или чрезмерно уверенно объявить успех. Поэтому
`finish_task` — запрос **проверить**, а не приказ пометить done.

Для `inspect` runtime ищет успешные чтения `order.py` и `test_order.py`, связанные
именно с этой задачей. Чтение при планировании хранится отдельно и не выдаётся за
исполнение задачи.

Для `fix` runtime ищет успешную запись `order.py` и сверяет текущий SHA-256 с тем,
который получился при записи. Если кто-то изменил файл позже, свидетельство устарело.

Для `test` runtime ищет успешный Bash с нужной командой и cwd, кодом возврата 0,
выводом unittest о выполнении хотя бы одного теста и совпадающим снимком дерева.

Почему не хватает `exit_code == 0`? Например, `pwd` тоже возвращает 0. Это не
запуск тестов. Даже unittest может успешно завершиться, не найдя ни одного теста.

Почему сверяется дерево? Тесты могли пройти на старом коде, а потом модель его
изменила. Старый успех уже не доказывает, что новая версия работает.

В `actual_result` сохраняются id вызовов, на которые опиралась проверка, и
краткое пояснение. На защите можно открыть JSON и показать связь, а не доверять
последнему текстовому ответу модели.

## 22. Снимки и хеши

Снимок — словарь вида «относительный путь → состояние файла».
Для каждого файла сохраняются:

- байты содержимого в Base64;
- SHA-256;
- режим доступа.

Base64 здесь **не шифрование**. Это способ положить произвольные байты в JSON.
Хеш тоже не заменяет содержимое: по нему можно проверить совпадение, но нельзя
восстановить исходный файл. Поэтому для отката нужны и байты, и хеш.

Список путей не менее важен, чем содержимое:

- был путь, а теперь нет — файл удалён;
- раньше пути не было — файл создан;
- путь остался, содержимое изменилось — файл изменён.

Пустой файл и отсутствие файла — разные состояния. В журнале отсутствие
представлено `None`, а пустой файл — записью с пустыми байтами и их хешем.

Перед побочным действием текущее дерево сравнивается с `expected_tree`.
Если оно отличается, значит, кто-то изменил проект после последнего
зафиксированного действия. Новый эффект останавливается с конфликтом.

После действия делаем новый снимок и сохраняем фактическую разницу. Это относится
к Bash тоже: если тест создал файл, он попадёт в журнал.

## 23. Как работает откат

Для каждого затронутого файла известны начальная версия и последняя версия
этого запуска. Команда `diff` строит по ним unified diff и показывает хеши.

Команда `rollback` сначала проверяет **все** файлы, которые собирается менять.
Если хотя бы один теперь отличается от последней версии агента, ничего не
перезаписывается. Причина: это может быть чужая работа, сделанная после агента.

Только после успешной общей проверки выполняются восстановления:

- изменённый файл получает исходные байты;
- созданный агентом файл удаляется;
- удалённый агентом файл создаётся с исходными байтами.

Файл, который создал пользователь после запуска и который агент не трогал,
не входит в список отката и остаётся на месте.

Два разных конфликта:

1. **До следующего действия** сверяется всё разрешённое дерево, чтобы не работать
   поверх незамеченных внешних правок.
2. **До отката** сверяются только затронутые запуском файлы, чтобы не мешать
   независимым пользовательским изменениям.

## 24. Если агент упал до фиксации diff

Допустим, запись успела изменить `order.py`, но после неё процесс упал.
Последний сохранённый журнал ещё не знает о новом содержимом.

Поэтому до отката нужно:

1. Показать разницу `uncertain-diff` относительно снимка перед попыткой.
2. Получить явное решение человека.
3. При `--adopt-changes` отнести обнаруженные изменения к этому запуску.
4. Только после разрешения неопределённости разрешить обычный откат.

Runtime не может по одному содержимому угадать, кто изменил файл во время
неработающего процесса. Человек явно принимает эту атрибуцию.

Если человек не согласен считать изменения агентскими, он может завершить
запуск с ошибкой. Система не должна молча переписывать спорные файлы.

## 25. Если упал сам откат

Откат нескольких файлов не атомарен целиком. Между восстановлением первого и
второго файла тоже может быть сбой.

Перед откатом сохраняется его намерение. После перезапуска статус будет
`rollback_uncertain`. Продолжение — только через явный повтор `rollback`.

Для каждого затронутого файла принимаются ровно два допустимых состояния:
последняя версия агента или уже восстановленная исходная версия. Если файл
имеет третье содержимое, это конфликт. Таким образом, уже восстановленные
файлы не мешают продолжить прерванный откат, а чужая правка всё ещё защищена.

Это не полноценная транзакционная файловая система. Для домашней работы
важно честно объяснить границу: атомарна запись одного state-файла и замена
одного файла, но не произвольный набор изменений всего дерева.

## 26. Что показывают тесты

Сначала запускаем тесты самого runtime:

```bash
python3 -m unittest discover -s tests -v
```

Это не то же самое, что `python3 -m unittest -v` внутри workspace.
Первое проверяет наш агентский код. Второе проверяет расчёт заказа, который агент исправляет.

Среди тестов есть:

- разные нарушения policy и схем;
- две команды в одном ответе модели;
- сохранение очереди между процессами;
- неизменность тестового файла;
- safe-подтверждения и отказ;
- запреты до утверждения плана;
- каждый бюджет отдельно;
- расход бюджета при падении;
- явный повтор неопределённой записи;
- запрет повтора неопределённого Bash;
- доказательство результата задачи;
- diff, создание, удаление, восстановление и конфликты;
- настоящий HTTP-обмен через локальный тестовый сервер;
- CLI в отдельных процессах с кодом падения 99;
- блокировка второго процесса на том же workspace.

Детерминированная модель позволяет тестировать runtime стабильно: от одного
прогона к другому ответы не меняются. Но это не доказывает качество живой модели.
Перед защитой нужно показать и отдельный запуск `--model api` со своим доступом.

## 27. Что здесь специально не усложняли

Нет базы данных, веб-интерфейса, очереди распределённых задач, нескольких агентов,
параллельного scheduler, установки зависимостей проекта через Bash и полного
языка shell. Это не требуется для проверки основных идей и затруднило бы защиту.

Зато сохранены важные границы:

- механизм работы не зависит от того, кто сгенерировал следующий tool call;
- policy не зависит от формулировок модели;
- результат действия сохраняется отдельно от её намерения;
- счётчики и прогресс переживают новый процесс;
- откат не затирает незаметно чужие правки.

## 28. В каком порядке разобраться за вечер

1. Запусти тесты runtime, чтобы убедиться, что среда работает.
2. Запусти auto-demo на копии workspace, утверди план, посмотри diff и откати.
3. Повтори в safe: увидишь отдельное подтверждение записи и Bash.
4. Прочитай `drive` и проследи один `read_file` через `step` → policy → executor → `done`.
5. Открой `.runs/имя.json` и найди соответствующие сообщения и calls.
6. Повтори демонстрацию сбоя после записи; сравни `expected_tree` и `uncertain-diff`.
7. Разбери `verify_task` и объясни, чем успех модели отличается от доказательства runtime.
8. Подключи свою доступную модель и сделай полноценный `api`-прогон.
9. Пройди вопросы из `defense.md` вслух, заглядывая в код только при необходимости.

Цель подготовки — уметь провести одно действие через все слои и объяснить,
что изменится при ошибке, отказе, падении и исчерпании бюджета. Если это понятно,
остальной проект перестаёт выглядеть большим набором несвязанных функций.
